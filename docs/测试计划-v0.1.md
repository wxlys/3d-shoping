## 1. 测试目标

1. 三端全流程功能可用，P0 用例全部执行并通过（或已知问题有清单）。
2. 秒杀高并发场景不超卖、限购生效、库存一致。
3. 排单队列与预计交付时间计算正确，取消/退款/改排期后重算正确并通知。
4. 文件上传安全（格式/大小/存储）与越权防护通过验证。
5. 产出可重复运行的接口自动化、CI 流水线和完整测试报告。

---

## 2. 测试范围

### 2.1 范围内

- 功能：登录注册、商品浏览、购物车、秒杀、定制上传/询价/报价/转单、订单支付（mock）、排单、打印进度、待取/取件码/确认收货/自动收货、退款、消息中心、后台管理（用户/商品/订单/询价/排单/财务/系统设置）。
- 接口：核心业务接口，覆盖正常、异常、边界、鉴权、越权。
- UI：Web 核心流程自动化（Selenium），App 冒烟自动化（可选，Appium）。
- 性能：秒杀下单（50 并发）、常规接口、排单重算。
- 安全：水平/垂直越权、XSS、SQL 注入、文件上传安全、登录锁定与会话、支付回调幂等。
- 兼容性：Chrome 最新两个版本、Edge；Android 9–14（模拟器 + 1 台真机）。
- CI：提交后自动构建 → 接口测试 → 报告。

### 2.2 范围外

- 真实支付渠道、推送、快递配送、优惠券/积分、扫码核销、周期结算。
- 材料仅 PLA/PETG；TPU、ABS、树脂不在本期。
- 单元测试（被测系统为开源改版，以系统级测试为主）。

## 3. 测试策略

### 3.1 分层

| 层级 | 策略 | 工具 |
|---|---|---|
| 接口 | 主自动化层，先 Apifox 梳理接口与生成用例，再迁移 pytest + requests | Apifox、pytest |
| Web UI | 只自动化 P0 核心稳定流程，其余手工 | Selenium |
| App UI | P0 冒烟，时间不足直接砍，不砍手工 | Appium（可选） |
| 性能 | 先 JMeter 设计场景，再 Locust 脚本化；主用 Locust | JMeter、Locust |
| 安全 | 手动越权/输入校验为主，扫描为辅 | OWASP ZAP、Burp（可选） |
| 兼容性 | 手工执行核心 P0 流程 | 浏览器、Android 模拟器/真机 |

原则：先工具后代码、保守推进；接口自动化优先，UI 自动化只做稳定核心。

### 3.2 用例设计

- P0：核心流程，必须全量设计并执行（登录、商品、秒杀、定制、询价、支付、排单、待取、退款）。
- P1：重要异常与权限场景，尽量执行。
- P2：次要功能与边界（导入导出、分享、消息中心细节等），抽样执行。
- 方法：等价类、边界值、判定表、状态迁移（订单/询价/文件/退款状态机是重点）。
- 需求跟踪矩阵（RTM）：需求 → 测试点 → 用例 → 缺陷 全链路可追溯。

### 3.3 AI 协作规则

- 人工编写测试方案与用例；AI 只做检查：找漏、查期望结果是否与 PRD 冲突、挑不可执行的步骤。
- AI 补充的测试点必须能追溯到 PRD，或明确标注“建议补充”，由人工确认后入库。
- AI 不得凭空发明需求；AI 生成的脚本脚手架必须人工运行验证。
- 保留 AI 使用记录，面试时能讲清“如何防止 AI 出错”。

## 5. 测试环境与数据

### 5.1 环境

- 被测系统：基于开源项目改版（具体项目与部署方式待选型后补充），本地部署：数据库（MySQL）、后端服务、Web 前端、App 包（Android）。

### 5.2 测试数据

- 预置数据：多角色用户（普通/封禁/管理员）、成品与秒杀商品、SKU 库存、分类。

- 数据管理：准备脚本化造数，测试后清理；数据库回滚方案待定（标记 PENDING）。

## 6. 缺陷管理

### 6.1 严重度与优先级

| 级别 | 定义 | 处理策略 |
|---|---|---|
| 严重（阻塞） | 核心流程不可用、数据错误、超卖、越权、支付/排单错误 | 立即修复或集中修复，修复后复测 + 回归 |
| 一般 | 功能可用但行为不符合预期 | 记录并评估，尽量修复 |
| 轻微 | 文案、样式、非关键体验问题 | 记录为已知问题清单，不阻塞发布 |

### 6.2 缺陷报告要素

缺陷编号、标题、所属模块、端、严重度/优先级、复现步骤、期望/实际结果、环境与版本、日志/截图、关联用例。

### 6.3 流程

发现 → 记录 → 分诊 → 修复（记录完整步骤与实际效果）→ 复测 → 回归 → 关闭；不修复的缺陷进已知问题清单（写明影响面），测试报告交代。

## 7. 测试报告

报告必须包含：

- 测试结论（是否达到发布标准）。
- 测试范围与版本环境。
- 执行进度：总用例/执行/通过/失败/阻塞/跳过。
- 缺陷统计：总数、严重度分布、缺陷密度、泄漏率。
- 覆盖率：需求覆盖率、用例覆盖率、接口覆盖率。
- 自动化情况：用例数、通过率、稳定性。
- 已知问题与风险（含影响面）。
- 图表：缺陷趋势折线、严重度分布饼图、模块通过率柱状图。

## 9. 6 周进度安排

| 周 | 任务 | 交付物 | 出口标准 |
|---|---|---|---|
| 1 | 开源项目选型、改版、环境部署；PRD 评审 | 选定项目、三端可运行、改版清单 | 核心业务流手动走通一遍 |
| 2 | 需求分析、测试计划细化、RTM、用例设计 | 测试计划、RTM、P0 全量用例 + P1 部分 | P0 用例评审通过（AI 检查 + 人工确认） |
| 3 | 手工功能执行 + 缺陷管理；Apifox 接口梳理 | 缺陷库、P0 执行完毕、接口用例就绪 | 阻塞缺陷清零或已集中修复，P0 通过率 100% 或有已知问题清单 |
| 4 | 接口自动化 + Web UI 自动化 | pytest 脚本、Selenium 脚本、Allure 报告 | 接口自动化可重复跑，通过率 ≥95% 稳定 |
| 5 | 性能 + 安全 + CI 流水线 | 性能报告、安全报告、Actions 流水线 | 流水线自动出报告，性能/安全问题已记录 |
| 6 | 全量回归、最终报告、简历素材 | 最终测试报告、项目介绍材料 | 报告数据完整，可面试讲清 |

每周留半天缓冲；落后时按顺序砍：App UI 自动化 → 性能场景 → P2 用例，不砍质量门。

## 10. 风险与应对

| 风险 | 应对 |
|---|---|
| 6 周时间不足 | 砍 App UI 自动化、性能场景、P2；保留接口自动化与 P0 手工 |
| 开源项目环境部署困难 | 第 1 周选型时必须跑通；跑不通直接换候选项目 |
| 秒杀并发在本地环境受限 | 降低并发目标或单独压测接口；正确性（不超卖）优先于性能数值 |
| UI 自动化不稳定 | 只自动化核心稳定流程，定时执行，失败人工确认 |
| 排单算法理解偏差 | 先用确定性 mock 公式，用例覆盖重算场景，结果人工核对 |
| 自己测自己改导致独立性弱 | 测试与修复动作分开记录，缺陷报告完整，报告数据不粉饰 |

## 11. 进入/退出标准

### 进入标准

- PRD 基线确认。
- 测试环境三端可运行。
- 测试数据就绪。
- P0 用例评审通过。

### 退出标准

- P0 用例 100% 执行；通过率 100%，或未通过项均在已知问题清单中并有影响面说明。
- 阻塞缺陷清零。
- 接口自动化通过率 ≥95% 且可重复运行。
- 性能目标达成或有明确结论与记录。
- 安全测试完成并输出问题清单。
- CI 流水线跑通并自动出报告。
- 最终测试报告完整。
